## Modifiche di design

- `EvalContext::regex_cache: HashMap<Vec<u8>, regex::bytes::Regex>` (era `HashMap<String, regex::Regex>`). Cache keyed sul pattern byte-string esatto, niente normalizzazione lossy.
- `compile_or_get_regex(re: &[u8]) -> regex::bytes::Regex` costruito via `RegexBuilder::new(...).unicode(false).build()`. La cache prima cercava in `HashMap::get(re)` poi compilava on-miss.
- `regex::bytes::Regex` adottato uniformemente per: operatori `~`/`!~` (Match/NotMatch), `match()` builtin, `sub`/`gsub`/`split` builtin con pattern, `RegexLiteral`, RS-regex e paragraph mode.
- Paragraph mode (`process_paragraph`) e RS-regex (`process_regex_rs`) ora leggono via `read_to_end` su `Vec<u8>` e splittano con `regex::bytes::Regex` (era `read_to_string` + `regex::Regex`).
- Nuovo helper `regex_pattern_from_bytes(&[u8]) -> String` in `src/types.rs`: promuove byte `>= 0x80` o non-UTF-8 a escape `\xNN` così il pattern resta UTF-8 valido (compatibile con l'API `Regex::new(&str)`) ma il matching su haystack `&[u8]` resta byte-esatto.
- `sub`/`gsub` ora rispettano POSIX su `&` (whole match) tramite `Replacer` closure + helper `expand_awk_replacement(&[u8], &Captures) -> Vec<u8>` che gestisce `&`, `\&`, `\\`, `\n` con n cifra (riferimento gruppo, anche se l'AWK puro normalmente non lo usa).
- RSTART/RLENGTH ora sono offset byte-esatti sul subject `&[u8]` (prima erano calcolati sul subject lossy con eventuali U+FFFD).

## Deviazioni dal piano (giustificate)

### 1. `src/parser.rs::decode_string_escapes` cambia signature `String → Vec<u8>`

Non era prevista dal plan 7.4. Causa: senza questa modifica il literal AWK `"\xC3"` veniva ancora decodificato come **UTF-8 dei byte del codepoint U+00C3** (cioè `[0xC3, 0x83]`) invece del **singolo byte raw 0xC3**. Con `\xC3` interpretato come 2-byte UTF-8, una regola tipo `BEGIN { RS = "\xC3+" }` non poteva mai matchare un input contenente il singolo byte alto 0xC3.

Era una latent gap di Phase 7 (decode escape non-byte-esatto) che il design doc annotava come BRIDGE 7.2→7.5 ("decode escape byte-esatto"), ma in pratica 4 dei 6 test RED 7.4 (i casi `high_byte_*`, `nul_byte`, `rs_*`) non potevano passare senza la patch. Decisione: anticipare il fix in 7.4 perché è strettamente necessario per GREEN e perché è un cambio meccanico (return type → `Vec<u8>`, escape `\xNN` produce `vec![NN]`). Rimangono per 7.5 le sole conversioni `printf %s`/`%c` byte-aware, che sono separate.

Locazione: `src/parser.rs` (la sola funzione modificata, +/- ~30 righe nel `match` su carattere di escape).

### 2. `regex::bytes::RegexBuilder::new(...).unicode(false).build()` ovunque, NON `regex::bytes::Regex::new`

`regex::bytes` ha di default **Unicode mode ON**, dove `\xC3` nel pattern significa *codepoint* U+00C3 (cioè i 2 byte UTF-8 `[0xC3, 0x83]`) e quindi NON matcha il singolo byte raw 0xC3 nell'haystack. Per ottenere semantica POSIX byte-esatta il flag Unicode deve essere disabilitato.

Decisione: helper interno `compile_or_get_regex` costruisce sempre tramite `RegexBuilder` con `.unicode(false)`. Costo di expressivity (no `\p{...}`, no `\d`/`\w` Unicode) è desiderato — POSIX vuole `\w` ASCII.

Locazione: `src/types.rs::compile_or_get_regex` (~10 righe).

### 3. Helper `regex_pattern_from_bytes` in `src/types.rs`

Il pattern source può arrivare:
- da un letterale `RegexLiteral(Vec<u8>)` già byte-clean,
- da un `Vec<u8>` runtime (es. `RS = some_var`) che non è necessariamente UTF-8 valido.

L'API `regex::bytes::Regex::new` accetta `&str` per il pattern (anche se il match è su `&[u8]`). Servono quindi due cose:
1. il pattern deve essere UTF-8 valido per costruire un `&str`;
2. i byte raw `>= 0x80` devono restare **byte literali**, non promossi a codepoint multi-byte.

`regex_pattern_from_bytes` itera sui byte e:
- per byte ASCII printable non-metacaratteri li lascia tali quali;
- per byte `>= 0x80` o per byte di controllo emette `\xNN`;
- preserva i metacaratteri regex (`.`, `*`, `+`, ecc.) intatti.

In questo modo un pattern byte `[0xC3, '+']` arriva al builder come la stringa UTF-8 valida `"\\xC3+"`, che con `.unicode(false)` matcha esattamente il byte 0xC3 seguito da uno o più.

Locazione: `src/types.rs::regex_pattern_from_bytes` (~15 righe) + chiamato dal site di `compile_or_get_regex`.

## Semantic deltas (bug latenti corretti)

### POSIX `&` in `sub`/`gsub`

Pre-7.4: la replacement string AWK veniva passata direttamente a `regex::Regex::replace_all(target, repl.as_str())`. Risultato: `&` nel replacement veniva trattato come **carattere letterale** invece che riferimento all'intero match. Esempio:

```awk
BEGIN { s = "abc"; sub(/b/, "[&]", s); print s }
# rawk pre-7.4:  a[&]c        (errato)
# POSIX/gawk:    a[b]c
```

Post-7.4: `replace_all` chiamato con un `Replacer` closure che invoca `expand_awk_replacement(&Captures)`:
- `&` → match completo `&captures[0]`;
- `\&` → `&` letterale;
- `\\` → `\` letterale;
- altri caratteri pass-through.

### RSTART/RLENGTH byte-offset esatti

Pre-7.4: il subject veniva passato a regex via lossy collapse (sequenze invalide → U+FFFD), quindi `start()`/`end()` del match erano offset nello string lossy, non nel byte buffer originale. Per subject ASCII non cambiava nulla; per subject byte alti coincideva solo per fortuna.

Post-7.4: il match è eseguito su `&[u8]` diretto, `m.start()` e `m.end()` sono già offset byte. RSTART = `m.start() + 1` (AWK è 1-based) e RLENGTH = `m.end() - m.start()` direttamente in byte.

## Follow-up tracked

1. **`expand_awk_replacement` arm `\<other>`**: l'attuale implementazione emette **sia il `\` che il byte successivo** (es. `\q` → `\q`). POSIX dichiara il comportamento *undefined*; gawk invece scarta il `\` (emette solo `q`). Decisione 7.4: **non scegliere ora**. Da sceglire in una future task (probabilmente come parte di 7.5 quando si rivede `awk_sprintf`); finché non scelto, lasciare il code commento documentato come "POSIX undefined / rawk preserves backslash, gawk drops it".

2. **`compile_or_get_regex` swallowing**: pattern non compilabili (es. parentesi non bilanciate) ritornano una regex vuota silente (comportamento pre-7.4, mantenuto). Andrebbe almeno un `// TODO POSIX:` marker o un BRIDGE 7.4→7.7 (acceptance) per decidere se diventa errore runtime con `errno`-like flag oppure se resta tollerante.

3. **`run_with_stdin` duplicato**: `tests/bytes_array_keys.rs` (7.3) e `tests/bytes_regex_match.rs` (7.4) ridichiarano la stessa helper function `run_with_stdin` (lancio binario `cargo run`, stdin pipe, raccolta stdout `Vec<u8>`). Prima che 7.5 introduca un terzo testfile (`bytes_printf` o simili) la helper va estratta in `tests/common/mod.rs` (mod condiviso del cargo test harness). Fare come primo step di 7.5.

## Lessons

- **Cascade single-commit conferma il pattern 7.2/7.3**: il type swap di `regex_cache` ha generato ~50 compile-error a cascata (`Regex` → `regex::bytes::Regex` non sono il **same type** anche se l'API è simile). Risolti tutti in un unico GREEN, senza commit rosso intermedio. R1>50 è ormai il pattern di Phase 7.

- **Closure `Replacer` è la via giusta per `&` POSIX in `regex::bytes`**: `replace_all` accetta `impl Replacer`, e una closure `|caps: &Captures| -> Vec<u8>` è più chiara e meno fragile che pre-processare la replacement string per escape (che peraltro confonderebbe `&` letterali con `&` semantici).

- **Unicode-off in `regex::bytes` è non-negoziabile per POSIX**: lo si scopre solo quando un test con `\xC3` come pattern letterale fallisce a runtime. Documentato in design doc pre-7.4 ma confermato dal test RED. Aggiungere checklist di setup quando si introduce `regex::bytes` in altri contesti: "ricorda `.unicode(false)`".

- **Lo scope creep su `parser.rs::decode_string_escapes` era giustificato, non over-build**: è un Phase 7 fix puro (byte-esatto, non semantica nuova), e non poteva essere rimandato perché bloccava 4 test GREEN. La regola "non aggiungere lavoro fuori dal piano" cede quando il lavoro fuori dal piano è una **dipendenza implicita** del piano corrente. Nota per future sub-phase: se un test RED non riesce a diventare GREEN con il solo lavoro pianificato, **prima** capire se la mancanza è una latent gap di Phase 7 (anticipa) o se è scope di una sub-phase futura (riformula il test, come fatto in 7.3.2).
